# PDF 解析方案对比报告（2026-10-18）

## 一、评测设计

- **评测集**：CFQA 543 道有效题（10 家公司），涉及 426 个标注答案页
- **判定口径**：答案的证据数字/文本是否出现在**标注页码本身**（与质检 gate2 同口径，不含 ±2 页窗口，四方案完全一致）
- **对比方案**：

| 方案 | 类型 | 调用方式 |
|------|------|----------|
| pymupdf（现状） | 文本层提取 | 本地，已有 `pages` 表（含页眉页脚清洗） |
| pdfplumber | 文本层规则提取 | 本地，`extract_text()` 原始输出 |
| PaddleOCR-VL-1.5 | 多模态文档解析 | SiliconFlow API，`<image>OCR:` prompt |
| DeepSeek-OCR | 多模态文档解析 | SiliconFlow API，输出 Markdown 表格 |

> GLM-OCR 与 OvisOCR2 在 SiliconFlow 模型列表中**未上架**（已核对 `/v1/models`），无法纳入本次对比；平台可用的专用文档 OCR 模型只有上述两个。

## 二、结果

| 方案 | 题级命中率 | 页码组命中率 | 平均字符/页 | 相对 pymupdf 新增/丢失 |
|------|-----------|-------------|------------|----------------------|
| **pymupdf** | **72.2%**（392/543） | **70.1%** | 1431 | — |
| DeepSeek-OCR | **71.6%**（389/543） | 68.9% | 1427 | +1 / -4 |
| pdfplumber | **71.5%**（388/543） | 69.4% | 980 | +2 / -6 |
| PaddleOCR-VL | **67.2%**（365/543） | 64.2% | 1936 | +3 / -30 |

> PaddleOCR-VL 有 7 页因 API 持续限流未取到（影响 7 题，约 1.3pp），已按缺失计。

## 三、结果分析

### 1. 文本层 PDF：规则提取天然占优

本批 44 份年报/招股书**全部带文本层**。文本层提取没有识别错误，OCR 的理论上限就是"还原出文本层已有的内容"——所以规则提取领先是结构性的，不是调参能追平的。

DeepSeek-OCR 以 71.6% 追平（差 0.6pp，在判分噪声内），是本次唯一达到"可替代"水平的多模态方案：它输出 Markdown 表格，数字完整、结构清晰，仅 4 题丢失。

### 2. PaddleOCR-VL 落后 5pp 的原因

- **缺少布局分析**：PaddleOCR-VL 官方 pipeline 先做版面分析、再按区域用不同 prompt（OCR / Table Recognition）调用；SiliconFlow 只提供 VLM 推理，直接整页喂 `<image>OCR:`，密集表格页效果打折
- **输出膨胀**：平均 1936 字符/页（pymupdf 1431），出现大量重复行（`(385) (%)`、`数量（人）` 反复输出），有效信息密度低
- **截断**：密集表格页超出 `max_tokens`，输出中途截断；把上限从 4096 提到 6144 重跑 65 页后，分数仅从 66.9% 提到 67.2%——**截断是次要因素，识别质量问题才是主因**
- 丢失的 30 题中 24 题是数字题，典型表现是整行/整表数字缺失

### 3. pdfplumber 与 pymupdf 的差异（8 题）

- 数字题两者判定**完全一致**，没有提取完整性问题
- 差异全部来自长文本题：pdfplumber 的换行/空格切分方式与 pymupdf 不同，影响 12 字以上公共子串的匹配
- 结论：两者等价，pymupdf 略优是因为我们已有的 `pages` 表做了页眉页脚清洗

### 4. 成本与延迟

| 方案 | 426 页耗时 | 成本 | 稳定性 |
|------|-----------|------|--------|
| pymupdf | < 1 分钟 | 0 | 确定 |
| pdfplumber | 约 1–2 分钟 | 0 | 确定 |
| DeepSeek-OCR | 约 7 分钟（6 并发） | API 计费 | 受 TPM 限流影响 |
| PaddleOCR-VL | 约 30 分钟（含重试） | API 计费 | 429 限流频繁 |

## 四、结论与建议

1. **当前选择正确**：对有文本层的年报，pymupdf 准确率最高、零成本、可复现，不需要更换
2. **OCR 的位置**：用于**扫描版 PDF（无文本层）**和图片型表格。本项目当前 44 份文档均无此问题；若未来扩充到老公司纸质年报扫描件，应引入 DeepSeek-OCR 而非 PaddleOCR-VL
3. **PaddleOCR-VL 要用完整 pipeline**：只调 VLM 推理接口（无版面分析）不能代表其真实水平；如要评估它，应本地部署 PaddleOCR 3.x 的完整流程
4. **不建议在当前语料上混用**：OCR 输出进入 RAG 会引入数字识别错误，反而增加数值核验负担

## 五、复现

```bash
python -X utf8 scripts/parse_compare.py                    # 四方案全量（首次约 30 分钟）
python -X utf8 scripts/parse_compare.py --limit 15         # 小样本
python -X utf8 scripts/parse_compare.py --sources pymupdf,pdfplumber   # 只跑本地方案
```

缓存位于 `db/parse_compare/`（按页缓存，重跑只补缺失页）；评测报告输出到 `reports/parse_compare_*.md`。

## 六、局限

- 只评测了"答案页"的提取质量，未评测全量语料进入 RAG 后的检索质量（分块、向量分布会带来额外影响）
- OCR 方案使用平台托管 API，非官方完整 pipeline，不能完全代表模型能力
- CFQA 答案页本身存在版本差异噪声（部分题的数字在下载的 PDF 版本中确实不存在），该部分对四方案一致拉低
