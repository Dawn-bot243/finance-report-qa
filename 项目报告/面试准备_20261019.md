# 项目面试准备：A 股财报智能检索问答系统

> 仓库：https://github.com/Dawn-bot243/finance-report-qa
> 技术栈：Python 3.13 · SQLite · FastAPI · Streamlit · DeepSeek · bge-m3 · bge-reranker · Docker

---

## 一、项目概览（STAR 式自我介绍，约 90 秒）

**S（背景）**：上市公司年报动辄 200–300 页，财务人员查一个数字要翻很久；直接问大模型又存在幻觉、无出处、口径混淆的问题。

**T（任务）**：构建一个财报问答系统，要求每个答案都能**精确溯源到 PDF 页码**，并用公开评测集量化效果。

**A（行动）**：

1. **数据层**：从巨潮资讯网抓取 10 家公司 44 份年报/招股书（10,683 页），逐页文本化；结构化指标采用「API 为主、PDF 提取为原文口径、出处回填」的三源架构，共 5,132 条带出处指标。
2. **检索层**：bge-m3 稠密向量 + jieba BM25 混合召回 → RRF 融合 → bge-reranker 精排；查询清洗去掉模板噪音。
3. **生成层**：DeepSeek 只依据检索上下文作答，行内引用【文档名 第N页】，数值核验不一致时标记待核实。
4. **Agent 层**：手写 function-calling 循环，5 个工具（检索/指标/对比/解释/核验）由模型自主选择；加入自校正检索（评估→重写→重检索）和多空辩论生成尽调报告。
5. **评估**：用 CFQA 543 道有效题做检索命中、数值判分、LLM judge 三档评估，并做 Agent/RAG、自校正/单次检索的同批对照。

**R（结果）**：端到端评估中检索 hit@10 **87.8%**、数值题 **86.2%**、叙述题 60.0%；Agent 在同一批 80 题上比固定流程高 **+10pp**；自校正检索 +7.5pp。后续把索引升级为语义子块并加入多查询检索，检索层 hit@10 提升到 **89.7%**。四道数据质量门全部 PASS。

## 二、系统架构

```
提问
 ├─ ⓪ 指标解释？ → 22 指标知识库直达（6ms）
 ├─ ① 公司+年份+指标？ → 结构化直答（8ms，as_reported 原文口径优先）
 └─ ② 其余 → 查询清洗 → bge-m3 + BM25 → RRF → bge-reranker → DeepSeek 生成
              → 行内引用【第N页】+ 数值核验 → 证据不足拒答

Agent 层：LLM 自主选择 5 个工具，最多 6 轮
  search_report（含自校正）/ get_metric / compare_companies / explain_metric / verify_numbers

多智能体：看多 Agent ⇄ 看空 Agent（各挂工具实时取证，3 轮）→ 主笔 Agent 汇总尽调报告

交付：FastAPI 8 个接口 + Streamlit 4 页签 + Docker Compose（nginx 反代/鉴权/限流）
```

## 三、关键技术决策与权衡（面试重点）

| 决策 | 备选方案 | 为什么选它 | 代价 |
|------|---------|-----------|------|
| **向量用 numpy 矩阵**，不用 Chroma | Chroma / Qdrant | Chroma 的 HNSW 索引在 Windows + Py3.13 反复损坏；9,810×1024 矩阵全量加载仅 ~40MB，内存暴力检索足够快 | 无增量索引、无元数据过滤（自己在 mask 里做） |
| **结构化指标走 API，不从 PDF 硬提** | 纯 PDF 表格提取 | 年报表格格式千变万化，规则提取覆盖率仅 58%；API 覆盖 74%，且更稳定 | 口径不一致 → 引入 `basis` 维度解决 |
| **三源指标 + 出处回填** | 单一数据源 | baostock/东财是重述口径，CFQA 答案是原文口径；用 PDF 提取做 as_reported，API 值容差匹配后回填页码 | 复杂度高：口径、匹配、冲突处理 |
| **手写 function-calling 循环** | LangChain / smolagents | 现有代码已是 requests 直连风格（openai SDK 在 py3.13 有 httpx 冲突）；需求简单，框架只会增加黑盒 | 需要自己实现 JSON 解析失败重试、去重、轮数控制 |
| **RRF 融合** | 加权分数融合 | 稠密分数（余弦）和 BM25 分数（无界）量纲不同，RRF 只用排名，无需调权重 | 丢弃了分数强度信息 |
| **先宽召回再精排** | 直接 top-k | 召回保 hit@10（87.8%），精排保喂给 LLM 的上下文质量（top-5） | 多一次 API 调用；rerank 故障时需降级 |
| **自校正只在 search_report 上启用** | 全局改 ask() | 影响面可控、可做同批对照；ask() 保持稳定基线 | 两条路径行为不一致 |
| **父子块：子块检索、父页回溯** | 1 页 = 1 chunk / 纯语义切分 | 子块更聚焦，父页保留上下文与【第N页】锚点 | 单独使用 hit@10 反而 -3.5pp（子块缺表头上下文），需配合多查询 |
| **多查询默认关闭** | 默认开启 | 检索层 +5.4pp，但 40 题端到端答案无提升、耗时 +45% | 保留开关，检索质量优先场景可开启 |

## 四、数据工程细节

### 数据规模

| 项 | 数量 |
|------|------|
| 公司 | 10 家（CFQA 问题数前 10） |
| 文档 | 44 份（40 主 + 4 候选版本，含 3 份招股书回退） |
| 页面 | 10,683 页 |
| 语义子块 / 父页 | 36,583 / 9,810 |
| 结构化指标 | 5,132（as_reported 3,763 / restated 1,369） |
| 指标定义 | 69 个 |
| CFQA 题目 | 740 条导入，543 条有效 |

### 质量门（四道）

1. **Gate1 文档完整性**：下载状态、sha256 唯一、页数范围、CFQA 页码不越界
2. **Gate2 答案命中**：答案数字/文本是否出现在标注页码（±2 页容差），**92.7% PASS**
3. **Gate3 指标交叉**：section2 vs 三大报表 / 跨年上年同期 / 招股书 vs 次年报告，容差 0.5%
4. **Gate4 提取率**：核心指标 ≥90%、报表核心行 ≥85%

### 口径设计（面试加分点）

同一个指标在年报里可能有两个值：
- **as_reported**：本年报原文披露值（与 CFQA 标准答案同口径）
- **restated**：API 提供的追溯重述值（后续年报调整过）

系统用 `basis` 字段区分，问答**优先取 as_reported**。这不是简单加个字段——它解释了为什么「API 数据很全但答案对不上」这个经典问题。

### 出处回填

API 值没有页码。做法：把 API 行与 PDF 提取行做容差匹配（0.5%），匹配上才回填 `evidence_doc_id / evidence_page_no`；不匹配只建立关联、不给页码，避免**引错页**。

## 五、检索链路

```
question
 → analyze_query（正则提取公司/年份/指标，不调 LLM）
 → clean_query（去公司名、年份、模板词；公司年份交给元数据过滤）
 → 稠密检索 top-20（numpy 余弦 + 元数据 mask）
 → BM25 top-20（jieba 分词）
 → RRF 融合 top-10
 → bge-reranker-v2-m3 精排 top-5
 → 生成
```

**为什么查询清洗很重要**：问题里的「两面针」「2022 年」「有哪些」这些词会稀释查询向量，而公司/年份已通过元数据过滤承担。实测 hit@10 从 4/10 提升到 9/10。

**rerank 的两个坑**：
1. API 返回结果**不保证按分数排序**，必须显式降序
2. 服务端变慢时单次可达 40+ 秒 → 加 12 秒超时 + 1 次重试，失败降级到 RRF 结果（保证可用性）

## 六、评估体系（面试重点：怎么证明有效）

### 评测集

CFQA 中文财报问答数据集，543 道有效题（排除：空页码 165 条、公司名错配 32 条、未披露类 34 条、版本差异 43 条）。

### 三档指标

| 指标 | 方法 | 说明 |
|------|------|------|
| 检索 hit@k | 答案页码（±2）是否在 top-k 候选中 | 结构化/FAQ 直答视为命中 |
| 数值题 | 数字容差 1%，含 10^-9~10^9 单位换算 | 1.48 亿 vs 148,432,611.28 判对 |
| 文本题 | DeepSeek-as-judge，0/1 判分 | 存在判分方差 |

### 同批对照（比绝对值更有说服力）

| 对照 | 结果 |
|------|------|
| Agent vs RAG 固定流程（80 题） | **57.5% vs 47.5%**（数值题 61.7% vs 46.8%） |
| 自校正 vs 单次检索（40 题） | **65.0% vs 57.5%**（4 次重写换来 +7.5pp） |
| PDF 解析四方案（426 答案页） | pymupdf 72.2% ≈ DeepSeek-OCR 71.6% ≈ pdfplumber 71.5% > PaddleOCR 67.2% |
| 5 家 vs 10 家（检索扩展性） | 原有公司子集 92.8%，新增 80.6% |

### 评估本身踩过的坑（很能体现严谨性）

1. **hit@10 名不副实**：评估调用 `ask()` 默认 top_k=5，top-10 实际只有 5 条候选 → 显式传 top_k=10
2. **数值判分假阴性**：「1.48 亿元」被正则切成 `48`，且单位换算只到 10^6，覆盖不了亿元↔元（10^8）→ 正则和 k 范围都修
3. **答案含推导百分比**：标注者算出来的百分比原文没有 → 有非百分数时只校验原文数字
4. **数据集噪声**：公司名错配（688550 下混入豪森股份 32 题）→ 导入时校验 `name_ok`

## 七、Agent 与自校正

### 工具设计

| 工具 | 能力 | 关键设计 |
|------|------|---------|
| search_report | 全文检索+生成 | 内含自校正 |
| get_metric | 指标点查 | 直接查结构化表，带出处 |
| compare_companies | 同业对比 | 2-3 家同报告期 |
| explain_metric | 指标解释 | 知识库直达 |
| verify_numbers | 数值核验 | 0.5% 容差 |

schema 的 description 里**动态注入 10 家公司清单和财年范围**——这是让模型正确选参的关键，比在 system prompt 里说更有效。

### 循环防护

- JSON 解析失败 → 作为 tool 消息回传让模型自我修正（不回抛）
- `(工具名, 参数)` 哈希去重，重复调用直接提示收尾
- 累计工具结果 >20,000 字符 → 注入「证据已足，请作答」
- 超 max_iters → 最后一轮不带 tools 强制总结

### 自校正（Corrective RAG）

```
检索 → 评估
        ├─ rerank top-1 ≥ 0.5 → 直接生成（零额外调用）
        └─ 低分 → LLM 复核「能否回答」
              ├─ 充分 → 生成
              └─ 不足 → 重写查询 → 重检索（最多 2 轮）
                    └─ 仍不足 → 拒答，不硬生成
```

**为什么用混合评估**：纯 LLM 每题多 2–3 秒；纯分数阈值不准。混合策略让高分题零成本、低分题才付 LLM 费用。

**局限（主动说）**：只改查询词，不改检索策略（top-k、BM25 权重、跨文档）；40 题只触发 4 次，说明分数阈值偏保守。

## 八、多智能体辩论

看多 / 看空两个 Agent 各挂全部工具实时取证，交替发言 3 轮，主笔汇总。

**工程要点**：
- 每轮重建消息（只带最近 2 轮对方发言），不保留历史 tool 结果——否则 3 轮后上下文爆炸
- 单方失败不中断辩论（记录异常占位继续）
- 主笔挂工具，可用 verify_numbers 核验，并如实标注核验不通过项

**实测**（两面针 2022，3 轮，321 秒）：
- 共识 5 条、分歧 5 条（每条含双方观点 + 证据强弱判断）、关键证据 14 项、风险提示 7 条
- 主笔能识别「看多方第 2 轮和第 3 轮口径摇摆」「看空方某指控被第 165 页数据证伪」

## 九、工程化与部署

- **API**：FastAPI 8 个接口（health/companies/ask/agent/kb/metrics/compare/metric_defs）
- **前端**：Streamlit 4 页签；Agent 页展示工具轨迹
- **部署**：Docker Compose 三服务（backend/frontend/nginx），数据卷挂载
- **鉴权**：`API_KEY` → `X-API-Key` / `Bearer`，`/health` 公开
- **限流**：nginx `limit_req`（/api/ 5r/s、页面 20r/s）+ 应用层固定窗口（默认 60/分钟/IP）
- **降级**：rerank 超时 12s → RRF；评估失败保守放行

**实测延迟**：非 LLM 接口 2–8ms、FAQ 6ms、结构化直答 8ms、RAG 2.1–3.6s、Agent 简单问题 2.2s / 复杂问题 10–60s。

## 十、三个最难的问题（STAR 案例）

### 案例 1：双版本年报互相覆盖（数据丢失级 bug）

- **现象**：同一公司同一年有两份文档（原版 + 更正版），指标数量比预期少一半
- **根因**：`metrics` 表唯一键是 `(code, fiscal_year, metric_key, source, column_label)`，**缺 doc_id**，两份文档的数据互相覆盖
- **修复**：唯一键加 `doc_id`
- **反思**：涉及「多版本数据」的表，唯一键必须包含版本身份

### 案例 2：hit@10 只有 5 条候选（评估造假）

- **现象**：hit@10 和 hit@5 数字完全一样
- **根因**：评估调用 `ask()` 没传 top_k，用了默认 5，`_retrieval_hit(…, k=10)` 实际只有 5 条
- **修复**：评估显式 `top_k=10`，结构化直答/FAQ 视为命中
- **反思**：**评估代码本身要有可信度检查**——两个指标完全相同就是异常信号

### 案例 3：结构化直答答非所问

- **现象**：问「分部收入」，系统按总收入回答；问「同比增长」，系统答绝对值
- **根因**：查询分析只匹配了指标别名，没有识别问题类型
- **修复**：三重精度守卫——分部/产品/地区类问题不直答、同比问题查 `_yoy` 指标、别名子串碰撞（「合同资产总额」⊃「资产总额」）加黑名单
- **反思**：**能用规则拦截的，不要交给模型**；直答路径要保守，宁可回退 RAG

## 十二、面试问答准备

**Q1：为什么用 RAG 而不是微调？**
A：三个原因。① 财报每年更新，微调需要重新训练，RAG 只需更新索引；② 微调无法给出处，而本项目核心要求是页码溯源；③ 数据量小（10,683 页），微调容易过拟合且成本高。RAG 的代价是检索质量成为天花板，所以后续重点都在检索和评估上。

**Q2：为什么不用向量数据库？**
A：数据规模 36,583 个子块 × 1,024 维，全量矩阵约 150MB，numpy 暴力检索仍在百毫秒级，没必要引入服务。Chroma 在 Windows + Py3.13 上 HNSW 索引反复损坏，Qdrant 需要额外部署。这是「规模决定架构」的判断——如果到百万级块，会换 FAISS/Qdrant。

**Q3：混合检索为什么用 RRF 而不是加权分数？**
A：稠密检索是余弦相似度（0–1），BM25 是无界分数，量纲不同，加权需要归一化和调参。RRF 只用排名（1/(k+rank)），对分数分布不敏感，鲁棒性好。代价是丢弃了分数强度信息——如果某一侧信号特别强，RRF 体现不出来。

**Q4：怎么证明你的系统有效？**
A：用公开数据集 CFQA 的 543 道有效题，三档指标：检索 hit@10 87.8%、数值题 86.2%、文本题 LLM judge 60%。更重要的是**同批对照**：Agent vs 固定流程（57.5% vs 47.5%）、自校正 vs 单次检索（65% vs 57.5%），控制变量后归因更可靠。

**Q5：检索和生成，哪个是瓶颈？**
A：检索和生成都有瓶颈，但我做过实验来定位。把索引切成语义子块后，检索层 hit@10 从 84.3% 提到 89.7%（配合多查询），但端到端答案准确率**没有变化**（65% vs 65%）。这说明：**正确页已经在 top-5 里，问题出在生成端没有稳定利用证据**——比如叙述题需要跨页整合、模型倾向于答「未披露」。所以下一步的重点不是继续提召回，而是改生成：更强的证据组织（如按主题聚合多页）、few-shot 示例、以及答案自评。

**Q6：怎么控制幻觉？**
A：四层。① 生成 prompt 强制「只依据上下文」；② 行内引用【第N页】；③ 数值核验（答案数字必须出现在所引页面）；④ 证据不足直接拒答（118/543）。Agent 层再加一层：自校正评估不通过就拒答，而不是硬生成。

**Q7：结构化数据和非结构化怎么融合？**
A：不是「融合成一个索引」，而是**路由 + 互相佐证**。查询分析命中「公司+年份+指标」走结构化直答（8ms），否则走 RAG（2–4s）；RAG 生成后再用结构化库核验数字。API 值与 PDF 原文容差匹配后回填页码，解决「结构化数据没出处」的问题。

**Q8：Agent 和 RAG 的区别？**
A：RAG 是固定管线（检索→生成）；Agent 把检索变成**模型手里的工具**，由模型决定调不调、调几次、调哪个。本项目实测 Agent 在数值题上 +15pp——因为它能主动选 `get_metric` 查结构化库，而 RAG 的路由是写死的。代价是 2 倍以上的延迟和成本。

**Q9：自校正的成本和收益？**
A：成本是每题多一次评估调用（低分题才触发 LLM 复核），收益是 40 题 +7.5pp。关键设计是**混合评估**：rerank 高分直接放行（零成本），低分才调 LLM。局限是只改查询词不改检索策略，且 40 题只触发 4 次，阈值偏保守。

**Q10：多智能体辩论的价值是什么？**
A：单一 Agent 容易「顺着一个方向论证」。两个对立角色互相挑错，主笔汇总时必须处理分歧。实测报告里主笔能识别「看多方两轮口径摇摆」「看空方指控被数据证伪」——这是单 Agent 很难做到的自我校正。代价是成本高（3 轮约 20–30 次工具调用）。

**Q11：数据质量怎么保证？**
A：四道质量门 + 口径设计。Gate1 文档完整性（sha256/页数/页码越界）、Gate2 答案命中 92.7%、Gate3 指标交叉（跨表/跨年/跨文档，容差 0.5%）、Gate4 提取率。另外处理了数据集噪声：空页码、公司名错配、推导百分比、版本差异。

**Q12：如果数据量扩大 100 倍怎么办？**
A：三处要改。① 向量检索换 FAISS/Qdrant（numpy 暴力检索 O(N) 不可行）；② SQLite 换 PostgreSQL，全文检索用 PG 的 tsvector 或 Elasticsearch；③ 嵌入和索引改为离线批处理 + 增量更新。架构上 RAG 部分不变，数据层替换。

**Q13：怎么控制成本？**
A：① 结构化直答绕过 LLM（12.5% 的题）；② 查询清洗减少无效检索；③ 自校正高分放行；④ rerank 失败降级不重试到底；⑤ 评估并发。目前一次复杂 Agent 问答约 2–3 轮、3–5 次 API 调用。

**Q14：这个项目最大的不足？**
A：**叙述题只有 60%，而且优化尝试没有传导到答案层**。我做了语义切分 + 多查询，检索层 hit@10 提到 89.7%，但端到端答案 65% 没变——说明瓶颈从检索转移到了生成（证据组织、拒答倾向）。另外评估样本偏小（Agent 40–80 题），虽然已改为 3 轮判分取多数，置信区间仍然较宽。

**Q15：你从这个项目学到什么？**
A：三件事。① **评估比功能更重要**——hit@10 名不副实、判分把 1.48 亿判错，都是评估 bug 掩盖了真实效果；② **能用规则拦截的不要交给模型**——结构化直答的精度守卫比 prompt 可靠；③ **数据口径是财报场景的核心复杂度**——as_reported vs restated 不解决，API 数据再全也答不对。

**Q16：多查询检索为什么在端到端没有提升？**
A：这是个有价值的负结果。检索层 543 题 hit@10 从 84.3% 提到 89.7%（+5.4pp），但 40 题 Agent 端到端答案准确率 65% vs 65%，完全没变。原因有两层：
① **提升的命中没进入生成上下文**——生成只用 top-5，而新增的命中大多落在 6–10 名；hit@5 虽然也从 78.1% 提到 82.1%，但 40 题里约 1.6 题的提升被判分波动抵消。
② **瓶颈已经转移**——正确页在 top-5 的题里，仍有一批答错，说明问题在生成端（跨页证据整合、模型倾向答「未披露」），而不是召回。
所以我把多查询**默认关闭**（耗时 +45% 换不到答案提升），保留开关。这个结论让我把下一步重点从「提召回」改成「改生成端的证据组织」。

**Q17：语义切分为什么单独用反而降了？**
A：子块平均 300 字，虽然更聚焦，但**丢失了页级上下文**——比如表格的表头「营业收入」和数值可能在同一个子块，但有些指标的说明在上一段。用子块文本做 rerank 时，模型缺少判断相关性所需的信息，导致排序变差（hit@10 -3.5pp）。改进是**子块检索、父页重排**：召回用子块，重排和生成用整页（截断 1200 字），这样 hit@10 回到 84.3%，配合多查询达到 89.7%。教训：**检索粒度和重排粒度可以不同，不必一致**。
